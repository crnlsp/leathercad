# Pre-1.0 product audit — the 1.0 boundary

**Date:** 2026-09-23 · **Base:** `main` at `449f62b` (F.0–F.7, 5.2 and 5.6 merged)
**Status:** Accepted with corrections at review (2026-09-23). §4 is the frozen 1.0 boundary, and §6 records how each decision was resolved.

This is a product-readiness checkpoint, not a third look at architecture or visuals. The question is
narrow:

> Can a new leathercrafter start with a blank project, make a useful pattern, edit it safely,
> understand its problems, save it reliably, reopen it later, and print a correct 1:1 result without
> fighting the application?

The repository is the source of truth: the roadmap, the product spec, the UI Foundations specs, the
ADRs, `file-format.md`, `printing.md`, the E2E suite, and the code. Every finding below cites where
it was checked. Classes: **(1)** already solved · **(2)** already on the roadmap · **(3)** partly
solved · **(4)** missing, required for 1.0 · **(5)** missing, better in 1.1+ · **(6)** not worth
adding.

---

## 1. Readiness in one paragraph

The **pattern core is ready**. Drawing, exact numbers, derived stitch lines, holes with corner
policy, seam allowance, folds, mirrors, dimensions, labels, the Problems channel, the leather
treatment of the canvas, and a 1:1 PDF all work. `phase-4-close-out.spec.ts` builds a complete card
holder end to end, then saves, reopens and exports it. What is **not** ready is everything around
that core, which decides whether a maker trusts the app with an evening's work:
- **Work can be lost without a word.** Closing the window, opening another file, and a crash all do
  it. There is also no way to start a new project short of restarting.
- **Printing is fixed at A4 portrait** from the app, and **a part bigger than the sheet cannot be
  printed at all**.
- **No physical print has ever been measured** (M5).

These are few, known and bounded. They are the 1.0 list.

**The edge-scoop feasibility check** (resolving §6.3). Everything below the editor already handles
arcs in drawn paths:
- the schema's path segments include arcs;
- persistence, evaluation, stitching and the PDF writer handle them;
- `Shapes.arcThroughPoints` builds an arc from three points.

It was tested on a 95 × 60 mm pocket with a scoop at three depths:
- **A stitch line along the three sewn sides works:** 173.5 mm and 47 holes, with no problems.
- A lines-only L-shape insets fine too.
- **Only a stitch line inset across the scoop fails** (`OFFSET_COLLAPSED`). A concave line-to-arc
  join is the Tier 2 offsetting of Phase 9 #11.

A scoop is a pocket's opening and is not stitched. **So the minimum enabler, arc segments in the
polyline tool, is an editor-only slice (3.9a) and is in 1.0.** Stitching across a concave arc join
is a documented 1.0 limitation, and a general curve editor stays 1.1+.

| Finding | Evidence | Class |

### 2.7 Direct manipulation

Features move by drag, and every other value is typed. Typing is the product's principle 4, "exact
numbers beat mouse precision". Handles for the stitch-line margin, the allowance or a dimension
would duplicate a typed field for a mouse gesture that is less exact. **(5)**, nothing for 1.0.

### 2.8 Stitching and assembly intelligence

The panel shows holes, spacing and **runs per side** (`Runs 24 · 45 · 23 · 45`), which is what a
maker checks by eye today. Automatic seam pairing and hole-count parity need an assembly model,
which parts do not have. **(5)**, already v1.2 in the product spec, and Phase 9 §4 item 6.

### 2.11 Error guidance

Problems name the feature and say what to do ("…Type at least 0.50 mm"). A disabled control says
why. A refused gesture says so beside the pointer. **(1).** One cheap gap, carried into §4: the
message for a file from a newer version says what happened, but not what to do. It should say to
update LeatherCAD.

### 2.12 Power-user workflow

Every tool has a single-letter shortcut. Also: Ctrl+Z and Ctrl+Shift+Z, Ctrl+S, Ctrl+Shift+S,
Ctrl+O, Ctrl+E, Delete, Escape, and Backspace in the polyline and arc tools. Duplicate lives in the
part menu, the mouse wheel zooms, and a double-click fits. **(1)** for 1.0. Two small gaps, neither
blocking:
- *fit* is only a double-click, and no hint mentions it;
- there is no Ctrl+N, which arrives with *New* in §4.

## 3. The `.lcp` compatibility policy for 1.x

Proposed, and written into `file-format.md` §4.5:

1. **Backward, always.** Every file any released version wrote opens in every later version.
   Migrations are immutable (invariant 9), and the corpus proves each one.
2. **A change to what is drawn, cut or printed bumps the format version.** An older build refuses
   the newer file with a sentence telling the maker to update. It never opens a file whose meaning
   it would silently get wrong. A new optional parameter an older build would ignore is exactly
   that case, because it would cut the wrong holes.
3. **A change that adds only metadata** keeps the version. Examples: a note, a colour, a display
   hint, which change nothing drawn, cut or printed. An older build opens the file and preserves the
   field through edits (#57).
4. **Unknown data is never silently discarded during load, save, or an ordinary in-place edit.**
   Two things are not carried over, and both are documented and tested (`file-format.md` §4.3):
   - the manifest, which describes its writer and is rewritten on every save;
   - the unknown fields of an object an edit **replaces or recomputes**. That means a derived
     source replaced by a path when a feature is frozen, and a drawn path and its segments
     recomputed when they are moved. The objects the edit keeps keep theirs.

No supported-version window is needed: rule 1 makes it unbounded, and rule 2 keeps it safe.

## 4. The 1.0 boundary

**Must be in 1.0.** Each item protects document safety, print correctness or the core workflow.

| # | Slice | What | Why it is required |
|---|---|---|---|
| 1 | **5.3a** | **Never lose work silently.** *New project*; a correct dirty state; *Save / Don't save / Cancel* before closing the window, opening a file, or starting a new project | Today three ordinary actions destroy work without a word |
| 2 | **5.3b** | **Crash recovery.** A recovery copy while there are unsaved changes, and a restore offer after an unclean exit that never overwrites a project file | The product spec's own data-safety requirement (§7) |
| 3 | **6.4a** | **Choose the paper.** Paper and orientation, written to the project setting 5.5 built | An A4 PDF on Letter paper is exactly where "fit to page" happens |
| 4 | **7.2a** | **Tile a part larger than the sheet.** Overlap, registration marks, and a tile label (row, column), at 1:1, with the verification marks on every sheet | Without it the larger half of leatherwork cannot be printed. **Needs approval (§6.1)** |
| 5 | **7.7** | **Measure a print with a steel rule and record it** (a person, not code) | M5, and CLAUDE.md forbids claiming 1:1 without it |
| 6 | **8.5a** | An app icon, a desktop entry and a production menu, on all three platforms | Basic release hygiene |
| 7 | **8.6** | **Linux, Windows and macOS builds**, signing and notarisation, a current README with a getting-started page, third-party notices, the newer-version message, and v1.0.0 | 1.0 is a public desktop release on all three platforms |

## 5. 5.3, re-scoped

| | 1.0? | Scope |
|---|---|---|
| **5.3a** Unsaved changes | **Yes** | *New project* (a button and Ctrl+N); a dirty state that is false for an untouched document and after undo back to the saved state; one guard used by closing the window, opening a file and *New*, offering *Save / Don't save / Cancel*. *Save* on an untitled document goes through *Save as*, and cancelling that cancels the whole action. An in-app dialog, like the delete dialog, so it is styled, keyboard-reachable and testable |
| **5.3b** Crash recovery | **Yes** | See the recovery design questions below |
| **5.3c** Recent files | No, **1.1** with 8.2 | Needs `preferences.json`. The OS file dialog already reopens the last folder |

The recovery design questions, answered for 5.3b's spec:
- **What is saved.** The document's parameters, as a `.lcp`, the same format and nothing more.
- **When.** At most every 60 s, only while the document is dirty, and never during a drag
  transaction.
- **Where.** `~/.local/state/leathercad/recovery/`, beside the log from the tooling checkpoint.
  Never next to the project, and never under the project's name.
- **Detection.** A recovery file that is still present at startup means the last session did not
  end cleanly, because a clean close or a save deletes it.
- **After a crash.** The app offers to restore. Restoring opens the copy as an **untitled, dirty**
  document, so the maker saves it where they choose.
- **Overwriting.** It never overwrites a project file. Declining keeps the copy until the next clean
  exit, so nothing is lost by saying no.

## 6. Decisions for the user, resolved at review (2026-09-23)

- **1. Tiling:** in 1.0, with the proposed scope.
- **2. The compatibility policy:** accepted. The "nothing discarded" wording is now precise
  (`file-format.md` §4.3, §4.5). Unknown data is never silently discarded during load, save or an
  ordinary in-place edit. An edit that replaces an object (freezing) or recomputes a primitive (a
  moved path) does not carry the old object's unknown fields, and that exception is documented and
  tested.
  - Checking this found four commands that rebuilt a source or mirror instead of copying it:
    `setShape`, moving a shape, moving a path, and moving a counterpart. So a plain move lost a
    source's unknown fields.
  - They now copy, and the contract tests fail without that change.
- **3. The edge scoop:** in 1.0 as 3.9a, after the feasibility check in §2.1.
- **4. The boundary replaces `product-spec.md` §5:** accepted.
- **Added at review:** Windows and macOS are 1.0 targets (8.6 and 7.7), with the credential steps
  recorded as release tasks.

The original questions follow.

1. **Tiling (7.2a) in 1.0.** It is the largest item and the only one that adds a printing capability.
   It follows the product spec's "four features" (§5), and it answers the 7.1 note that "sometimes
   you need multiple pages". Moving it to 1.1 would make 1.0 an A4-sized-items release.
2. **The compatibility policy in §3**, in particular rule 3: metadata-only additions keep the
   format version.
3. **The edge scoop.** The product spec's representative session (a pocket with a curved thumb
   scoop) cannot be drawn in 1.0. A round cut-out can; an edge notch cannot. Accept that for 1.0,
   or pull in the smallest enabler (arc segments in the polyline tool) as a 1.0 item.
4. **This boundary replaces `product-spec.md` §5's list** as the definition of 1.0. §5 now points
   here and keeps its rationale.

## 7. The first 1.0 slice: 5.3a

**Chosen because:**
- it closes the most common way to lose work, in every session, for every user;
- it needs no product decision;
- it is small;
- 5.3b builds on it, because recovery keys off the same dirty state it corrects.

Tiling is the larger capability, but it waits on decision 1. Paper choice is next after 5.3b.
